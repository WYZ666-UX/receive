> 评审对象：《双端对接手册-设计思路与参考代码》（2026-11-01 15:04）
> 评审方：显示端
> 评审范围：控制帧（`A5 5B`）、数据帧（`A5 5A`）、会话状态机、命令表
> 结论：协议整体清晰可用，CRC 与常量定义扎实；以下 6 项会在真实联调中变成故障，建议联调前修订。

---

## 0. 结论摘要

| 级别 | 数量 | 含义 |
|---|---|---|
| **P0** | 6 条 | 会导致状态分裂、联调卡死、误判掉线，必须改 |
| **P1** | 4 条 | 影响可观测性、可测试性，建议改 |
| **P2** | 3 条 | 带宽/扩展性优化，可选 |

其中 4 条只需改文档契约（不动代码），6 条需要采集端小改代码。

---

## 1. P0 · 必须修改

### 1.1 ACK 必须原路返回，并定义重复命令去重窗口

**现状**：手册规定"两个通道共用同一套命令表"，但未定义 ACK 走哪条链路。

**风险**：
显示端从 UDP 发 `SET_TIME_BASE`，采集端若从串口回 `ACK_TB`，显示端收不到 → 按规则重发 3 次 → 判定失败，但采集端**已经切换了档位**。两端状态就此分裂，且显示端会一直显示旧档位。

**建议**：
1. **谁来的请求，ACK 原路返回**：UDP 来的回 UDP（回到报文源 IP:端口），串口来的回串口。
2. 规定去重窗口：**200 ms 内收到相同 `(CMD, DATA)` 视为重复**，不重复执行，只把上一次的 ACK 重发一遍。
3. 幂等性只保证"结果一致"，不保证"不重复回包"，去重窗口是必要补充。

**实现要点**（采集端）：
```c
/* 去重记录 */
typedef struct { uint8_t cmd; uint8_t data[8]; uint8_t len; uint32_t ms; uint8_t ack[16]; uint8_t ack_len; } LastCmd;

/* 收到命令时 */
if (last.cmd == cmd && last.len == len && !memcmp(last.data, data, len)
    && (now_ms - last.ms) < 200u) {
    回放 last.ack;   /* 不执行 */
} else {
    执行；保存 cmd/data/ms/ack；
}
```

### 1.2 新增 `GET_STATUS (0x03)`

**现状**：命令表只有 SET 类命令，没有查询命令。

**风险**：
显示端上电、或从 LOST 恢复后，无法知道采集端当前档位/通道/运行状态。UI 显示 `tb=2`，采集端实际 `tb=4`，只能靠用户再点一次按钮才对齐。联调时表现为"按钮点了没反应，但实际已经变了"。

**建议**：新增一条只读命令。

| CMD | 名称 | 方向 | DATA | 应答 |
|---|---|---|---|---|
| `0x03` | `GET_STATUS` | 显→采 | 无（LEN=0） | `0x83` `ACK_STATUS` |
| `0x83` | `ACK_STATUS` | 采→显 | 8 字节（见下） | — |

`ACK_STATUS` DATA 布局（小端）：

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | `TIME_BASE` | 0..4 |
| 1 | `CH_EN` | bit0=CH1 bit1=CH2 bit2..4=D1..D3 |
| 2 | `RUN` | 0=停 1=跑 |
| 3 | `TRIG_FLAG` | 当前恒 0（未实现） |
| 4-5 | `TRIG_LEVEL` | 恒 0 |
| 6-7 | `SQUARE_HZ` | 方波频率，小端 |

**实现要点**：HELLO_ACK 之后、PING 之前不发；显示端在进入 UP 状态时主动发一次 `GET_STATUS`。

---

### 1.3 `HELLO_ACK` 携带状态

**现状**：`HELLO_ACK [VER]`，只有版本号。

**风险**：同 1.2，恢复后状态未知。若不想加 `GET_STATUS`，至少让 HELLO_ACK 带状态。

**建议**（二选一，推荐同时做）：

```
0x81 HELLO_ACK  DATA = [VER, TIME_BASE, CH_EN, RUN]      （LEN=4）
```

**兼容策略**：显示端按 `LEN` 判断——`LEN==1` 为旧版（只有 VER），`LEN>=4` 带状态。无需升协议版本。

---

### 1.4 约定采集端 IP 与命令端口

**现状**：手册只写"采集端发到 `192.168.9.11:5000`"，未写采集端自身 IP，也未写采集端在哪个端口收命令、ACK 回到哪个端口。

**风险**：直连场景无 DHCP，双方必须静态 IP。缺这一项联调第一步就卡住。

**建议**（推荐采用"同端口对称"方案，实现最简单）：

| 项 | 值 |
|---|---|
| 显示端 IP | `192.168.9.11`（静态） |
| 采集端 IP | `192.168.9.12`（静态，建议值，可协商） |
| 子网掩码 | `255.255.255.0` |
| UDP 端口（**双方共用**） | `5000` |
| 连接方式 | 网线直连（MDI/MDIX 自适应），无需交换机 |

采集端与显示端都绑定 `UDP:5000`（IP 不同，端口不冲突）。显示端从 `5000` 发命令到采集端 `5000`，采集端把 ACK 发回**报文源地址**（即显示端 `192.168.9.11:5000`）。这样一条 socket 同时收发，不需要额外端口。

---

### 1.5 UDP 包必须按包头分流，不能直接喂给 `DISP_Feed`

**现状**：手册第二节写明"UDP 也支持控制命令"，但 `DISP_Feed` 只认 `A5 5A`，遇到 `A5 5B` 会走 `bad++` 并丢弃。手册未写分流规则。

**风险**：
UDP 上出现的控制帧被计入 `bad`，导致"坏帧计数"虚高。调试时看到 `bad` 上涨会误判为链路质量差，实际是正常的控制帧。

**建议**：在手册第七节明确写出分流规则，显示端照此实现：

```c
/* UDP 收到一个包后，先分流 */
if (p[0] != 0xA5)            { bad++; }
else if (p[1] == 0x5A)       { DISP_Feed(&ctx, p, len);      /* 数据帧 */ }
else if (p[1] == 0x5B)       { CMD_Handle(&ctx, p, len);      /* 控制帧/ACK */ }
else                         { bad++; }
```

同时注明：`bad` 只统计"既不是 5A 也不是 5B"或校验失败的包。

---

### 1.6 规定 `RUN=0` 时的心跳行为

**现状**：40 fps 数据帧本身承担"链路活着"的证据；但 `SET_RUN 0` 后是否停发数据帧、PING 是否继续，手册未定义。

**风险**：
若停发数据帧且停发 PING，显示端会在 3 秒后判定 LOST，UI 弹"链路丢失"，但采集端其实正常待机。

**建议**（二选一，推荐方案 A）：

| 方案 | 规则 |
|---|---|
| **A（推荐）** | `RUN=0` 时数据帧降速到 **1 fps**（每 1s 发一屏），PING/PONG 照常 |
| B | `RUN=0` 时停发数据帧，但 **PING 必须继续**（1s 间隔），PONG 照常 |

无论哪种，手册都要写明"LOST 判定依据是 3s 内未收到**任一** 5A/5B 帧，而不是 3s 内未收到数据帧"。

## 2. P1 · 建议修改

### 2.1 用保留字段承载时间戳 `TICK_MS`

**现状**：数据帧头偏移 16-19 为"保留，置 0"，4 字节完全浪费。

**风险 / 收益**：
显示端无法计算真实帧间隔与抖动，无法检测"采集端卡住"（只能等 3s 超时）；也无法做跨帧时间对齐（低频测量需要多帧累计）。

**建议**：把偏移 16-19 改为 `TICK_MS`（uint32 小端，采集端 1ms 计数）。帧长仍为 1272，**零成本**。

| 偏移 | 原字段 | 建议字段 |
|---|---|---|
| 16-19 | 保留（置 0） | `TICK_MS`（uint32，小端） |

显示端可用它计算：
- 帧间隔抖动（判断是否掉帧、卡顿）
- 跨帧累计测量低频信号（把多帧按时间戳拼接）

---

### 2.2 补齐丢帧统计口径

**现状**：`incomplete` 只统计"半帧未配对"。连续丢整帧（seq 从 100 跳到 105）无法检测。

**风险**：显示端报告的"丢帧数"可能恒为 0，与实际不符。

**建议**（显示端实现 + 手册补说明）：

```c
/* 显示端维护期望序号 */
if (seq != expected_seq) {
    lost += (uint16_t)(seq - expected_seq);   /* 无符号差，自动处理回绕 */
}
expected_seq = seq + 1;
```

手册第六节补一句：`FRAME_SEQ` 为 uint16，40 fps 下约 27 分钟回绕一次，配对逻辑用无符号差值即可正确跨回绕。

---

### 2.3 明确"两包齐了才允许读"的调用约定（或改双缓冲）

**现状**：`DISP_Feed` 收到 PART0 就立即写入 `cur.ch1[0..249]`，此时 `cur` 是半新半旧。

**风险**：若显示端在中断/独立任务里读取 `cur`，会画出"一半上一帧、一半这一帧"的波形，表现为瞬间撕裂。

**建议**（二选一）：

| 方案 | 做法 |
|---|---|
| A（推荐，零成本） | 手册明确定义：**只有 `DISP_Feed` 返回 1 时才允许读取 `cur`**，其余时刻显示端不得访问 |
| B（更稳） | 参考实现改为双缓冲：`cur` 与 `next` 分离，成帧后指针交换 |

方案 A 只需要在手册第 8.2 节补一句调用约定，采集端代码不用改。

---

### 2.4 统一帧率口径

**现状**：第二节写"每 25 ms 发一屏"（40 fps），第十一节写"帧率上限 30 fps"。

**风险**：显示端缓冲深度、UI 节流策略、带宽估算都会按这个数字设计，两个值对不上会导致预估值偏差 33%。

**建议**：只在文档保留一处，并明确：

- 若取 **25 ms / 40 fps**：带宽 = 2 × 1272 B / 25 ms ≈ **101.8 kB/s**
- 若取 **33.3 ms / 30 fps**：带宽 ≈ **76.3 kB/s**

同时在第十一节备注实际测试帧率（`udp_recv_test.py` 的实测值），避免文档与实测再次不一致。

## 3. P2 · 可选优化

### 3.1 12bit 打包（仅当需要串口回退时）

**现状**：模拟块 16bit 直存，250 点 × 4 B = 1000 B/包。

**说明**：以太网带宽充裕，**当前不需要改**。但若将来出现"以太网不可用、退回串口传数据"的场景，1000 B 模拟块在 921600 波特率下会明显吃紧（对比 12bit 打包的 750 B，可省 33%）。

**建议**：仅在协议版本升级（VER=2）时考虑，不影响本次联调。

### 3.2 `CH_EN` 让采集端实际生效

**现状**：手册已承认"打包时无条件跑满所有通道，关通道不缩短帧长、不省带宽"。

**说明**：帧长不变的前提下，至少可以让采集端**跳过未使能通道的 ADC 转换与打包**，节省 CPU 与功耗。帧结构不变，显示端无感知。

**建议**：`CH_EN=0` 的通道填 0（或填中值 2048），但不再启动对应 ADC 通道的采样。

### 3.3 扩展性：`TOTAL_PARTS` 与可变帧长

**现状**：`NSAMP=250`、`len==1272`、`PART∈{0,1}` 全部硬编码。

**说明**：当前 500 点够用，**不建议现在改**。仅记录：若将来点数改为 250 或 1000，需要升 `VER` 并同步修改显示端的固定校验。属于版本升级壁垒，不是当前缺陷。

## 7. 不需要修改的部分（已确认良好）

| 项 | 评价 |
|---|---|
| CRC-16/CCITT-FALSE，自检 `0x29B1` | 正确，显示端现有实现可直接复用 |
| CRC 覆盖含包头 `A5` | 严谨，能检出包头篡改 |
| ACK 回"实际生效值" | 设计聪明，一次比较即可判定接受与否 |
| 离散档位拒绝 / 连续量钳位 | 语义区分合理，贴合操作直觉 |
| 幂等性要求 | 为 ACK 重发提供正确前提 |
| `DISP_Feed` 的 PART 乱序处理 | 逻辑正确，先到 PART1 也能正确成帧 |
| 时基档位表与采样率 | 与显示端现有 5 档完全一致 |
| 命令帧长度 `6+LEN` 与 CRC 范围 | 定义清晰，无歧义 |
