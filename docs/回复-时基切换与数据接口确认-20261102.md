## 0. 摘要：三处必须先修正，否则解析会出错

| # | 你们文档里的写法 | 实际协议 | 后果 |
|---|---|---|---|
| **1** | 模拟块 `20-269`（1000B）、数字块 `270-1269`（1000B）| **模拟块 `20-1019`（1000B）、数字块 `1020-1269`（250B）** | **波形完全错乱** |
| **2** | `TRIG_FLAG`：0=自由运行，1=已触发 | **`TRIG_FLAG` = 配置的触发源**（0..5）| 触发状态判断错 |
| **3** | `dt = 10*tb/499` | **`dt = 10*tb/500 = tb/50`** | 0.2% 频率误差 |

### 修正 1：载荷布局（**最严重**）

你们的表格里偏移和长度是自相矛盾的（`20-269` 只有 250 字节却标 1000）。

**正确的载荷布局（`frame.c` 实际输出）：**

| 块 | 偏移 | 长度 | 内容 |
|---|---|---|---|
| 模拟块 | **20 – 1019** | **1000** | 250 点 × 4 字节：`CH1_lo, CH1_hi, CH2_lo, CH2_hi` |
| 数字块 | **1020 – 1269** | **250** | 250 点 × 1 字节，低 3 位 = `D3 D2 D1` |
| CRC16 | 1270 – 1271 | 2 | 覆盖 `0..1269`，小端 |

**关键：这是两块连续，不是逐点交织。**

```python
# 正确解析
pl = pkt[20:1270]
ch1 = [(pl[i*4+0] | pl[i*4+1]<<8) for i in range(250)]
ch2 = [(pl[i*4+2] | pl[i*4+3]<<8) for i in range(250)]
dig = [pl[1000+i] & 0x07 for i in range(250)]

# 错误写法（会得到垃圾波形）
# for i in range(250): ch1[i]=pkt[20+i*5]; ch2[i]=...; dig[i]=pkt[20+i*5+4]
```

### 修正 2：`TRIG_FLAG` 不是布尔量

| 字段 | 语义 |
|---|---|
| `TRIG_FLAG`（偏移 9）| **配置的触发源档位**：0=关闭，1=CH1，2=CH2，3=D1，4=D2，5=D3 |
| `TRIG_POS`（偏移 10-11）| **这一帧有没有对齐成功**：`0xFFFF` = 没找到触发；否则 = 触发点在 500 点中的位置 |

判断"自由运行 / 已触发"**看 `TRIG_POS`，不要看 `TRIG_FLAG`**：

```
TRIG_POS == 0xFFFF  ->  自由运行（不管 TRIG_FLAG 是几）
TRIG_POS != 0xFFFF  ->  已对齐，且 TRIG_POS 恒等于配置的 pre
```

### 修正 3：采样间隔公式

一屏 = 10 格 × 50 点/格 = 500 点，所以**每格 50 个点**：

```
dt = tb / 50 = 10 * tb / 500        （正确）
dt = 10 * tb / 499                  （你们文档，偏小 0.2%）
```

用 `dt = 1 / 该档采样率` 也一样，见第 1 节。

## 1. Q1 · 五档是否都支持？实际采样率？

**五档全部支持。** 实测值（不是理论值）：

| 档位 | `TIME_BASE` | 每格 | **实测采样率** | **采样间隔 dt** | 一屏（500 点）时长 |
|---|---|---|---|---|---|
| 10ms | 0 | 10 ms | **5 000 Sa/s** | **200 µs** | 100 ms |
| 5ms | 1 | 5 ms | **10 000 Sa/s** | **100 µs** | 50 ms |
| 1ms（默认）| 2 | 1 ms | **50 000 Sa/s** | **20 µs** | 10 ms |
| 500µs | 3 | 500 µs | **100 000 Sa/s** | **10 µs** | 5 ms |
| 100µs | 4 | 100 µs | **约 450 000 Sa/s** | **约 2.2 µs** | 约 1.1 ms |

**限制说明：**

- 采样率范围 **5 000 ~ 500 000 Sa/s**
- **第 4 档（100µs）实测约 450 000 Sa/s，是标称值的 90%**，不是 100%。
  原因是 ADC 时钟 27 MHz（F7 上限 36 MHz，27 已是最大合法分频），
  单次转换 0.556 µs，1 MHz 触发率下已达物理极限。
  如果你们按 500 000 算，这一档会偏大 **11%**；
  **建议第 4 档按实测 450 000 标定**，或者接受这 11% 误差（前四档都是精确的）。

## 2. Q2 · 切档是否在帧边界完成？需要丢 1 帧稳定期？

**已实现帧边界切换，不需要你们额外丢帧。** 这是本次固件改动（hex 13:34）。

### 机制

```
收到 SET_TIME_BASE
   ↓
立刻回 ACK 0x90（实际生效档位）
   ↓
立刻改采样率（TIM1 的 ARR）
   ↓
⏳ **丢弃所有帧，直到攒够 500 个新档位的样点**（这段时间遥测里 tbskip 递增）
   ↓
攒够 → 恢复正常发帧，帧头 TIME_BASE = 新档位
```

### 为什么必须这样

切档时环形缓冲里还是**旧采样率**采的样点。如果立刻发帧，
那 500 个点里会混着两种采样间隔 —— 正好是你们说的"半帧旧时基 + 半帧新时基"。

### 重同步要多久（= 你们会看到多久的空档）

| 新档位 | 需要攒 500 点 | 约等于 |
|---|---|---|
| 10ms | 500 / 5000 = **100 ms** | 约 2 帧 |
| 5ms | 500 / 10000 = **50 ms** | 约 2 帧 |
| 1ms | 500 / 50000 = **10 ms** | 不到 1 帧 |
| 500µs | 5 ms | 不到 1 帧 |
| 100µs | 约 1.1 ms | 不到 1 帧 |

**所以：10ms 档切档时会丢 2 帧左右，其余档几乎无感。请把这几帧的丢失排除在 `DROP` 统计之外**（可以用 `TIME_BASE` 变化后的前 2~3 帧来识别）。

### 其他保证

- ✅ 帧头 `TIME_BASE` 永远是**这一帧实际使用的档位**，不会是"请求但没生效"的值
- ✅ `SEQ` **不因切档而重置**，继续递增
- ✅ 两包（PART 0/1）**同 SEQ、同 TB、同 CH_EN、同触发字段**

## 4. Q4 · 不支持的档位回 NACK 还是降级？

**时基命令永远不 NACK。**

| 情况 | 采集端行为 |
|---|---|
| `SET_TIME_BASE 0..4` | `ACK_TB [请求的档位]`，档位真的切换 |
| `SET_TIME_BASE ≥5`（越界）| **`ACK_TB [当前档位]`**，档位**保持不变** |
| `SET_TIME_BASE` 长度 0（LEN=0）| `NACK 0x02` |

**建议你们按"ACK + 实际档位"来写，不要依赖 NACK。**

### 原因码定义（只在真正非法时用）

| 码 | 含义 | 触发场景 |
|---|---|---|
| `0x01` | 未知命令 | CMD 不在表里 |
| `0x02` | 参数越界 / 长度不足 | 如 `SET_TRIGGER` 负载 <6 字节、`src≥6` |
| `0x03` | 版本不符 | `HELLO` 的 VER ≠ 1 |
| `0x04` | 忙 | 钩子函数未注册 |

## 5. Q5 · 500 点是否严格等间隔？

**点与点之间：严格等间隔，无抽取、无平均、无死区。**

`第 k 点时刻 = TICK_MS窗口末 + (k-499) × dt`，`dt` 见第 1 节。

### ⚠️ 但有一处必须提前说明：一个"点"内的 CH1 和 CH2 差半个点间隔

ADC 每次触发只转换 **1 个通道**（这是本芯片 + 本配置的实测行为），所以：

| 通道 | 采样时刻 | 相对关系 |
|---|---|---|
| **CH2**（麦克风，协议 CH2）| 触发 `2k` | 基准 |
| **数字通道** | 触发 `2k` | **与 CH2 完全同刻** |
| **CH1**（电位器，协议 CH1）| 触发 `2k+1` | 比 CH2 晚 **1 次触发 = 半个点间隔** |

**换算成格数**（1ms/格，1 格 = 50 个点 = 1ms）：

```
半个点间隔 = 0.5 × 20µs = 10µs = 0.01 格
```

**远小于评分要求的 0.2 格**，可以忽略。但你们如果做"同一信号接模拟+数字，测相位偏差"，要知道这个 0.01 格的存在。

> 如果验收时老师把同一信号接 CH1 和数字通道，看起来会有 0.01 格偏移 —— 这是硬件限制，不是 bug。

## 7. Q7 · TICK_MS 是首点时刻还是发送时刻？

**是发送时刻**，准确说是"这一帧打包完成、即将发出的时刻"，由 `HAL_GetTick()` 在打包前取一次。

| 项 | 值 |
|---|---|
| 精度 | **毫秒**（够用，帧间隔 25~50ms）|
| 与窗口的关系 | `TICK_MS` ≈ 点 499 的采集时刻 + 打包耗时（<1ms）|
| 两包是否相同 | **相同**（同一帧只取一次，已实测修过这个 bug）|

**如果你们需要"点 0 的时刻"**：

```
点0时刻 ≈ TICK_MS - 500 / 采样率
```

### 用途提醒

`SEQ` 是逻辑帧号，`TICK_MS` 是真实时间。两者一起用可以区分：

- `SEQ` 跳号但 `TICK_MS` 间隔正常 → **中间的网络包丢了**
- `TICK_MS` 间隔变大 → **采集端卡了**（比如切档重同步、或链路断了）

## 8. Q8 · 关闭通道时载荷是否保持完整布局？

**是。长度永远不变：250×4B + 250×1B。**

关闭的通道**填 0**（不是跳过、不是缩短帧）。

### 实测证据

```
CH_EN = 0x1F（全开）  ->  CH1 max=1769, CH2 max=1311, 数字 0..4
CH_EN = 0x01（只开 CH1）
   -> 帧头 CH_EN = 0x01
   -> CH2 的 500 个点  全部为 0     （max=0）
   -> 数字通道 500 个点 全部为 0     （max=0）
   -> **CH1 完全不受影响**        （max=1769，关闭前也是 1769）
CH_EN = 0x00（全关）
   -> 整帧 1250 字节载荷全为 0
   -> **但帧仍然照发**（不会停发让你们空屏）
```

**所以你们可以按固定长度解析，完全不用管 `CH_EN`。** 关掉的通道拿到 0，画不画由你们决定。

## 9. Q9 · `TRIG_POS` 是否恒等于 `pre`？`pre=50` 接受吗？

### 恒等于 `pre % 500`

这是一个**刻意的设计**，不是巧合：

```
找到触发点后：窗口起点 = (触发点 + 缓冲深度 - pre) % 深度
            触发点在帧内的位置 = pre % 500
```

因为窗口总是"从触发点往前推 pre 个点"开始，所以**触发点必然落在帧内第 pre 个位置**，与信号形状无关。

**对你们的好处**：`TRIG_POS` 是常数 → **不需要做对齐平滑**，直接按固定位置画就行，波形永远不滑。

### `pre = 50` 接受 ✅

有效范围 0 ~ 499。`pre=50` 表示触发点在屏幕 10% 位置，正是你们现在用的值。

（注意：`pre` 超过 500 时会取模，例如 `pre=550` 等价于 `pre=50`。）

### 触发流程核对

```
你们发 0x12: [src, edge, level_lo, level_hi, pre_lo, pre_hi]   ← 6 字节！
我们回 0x92: [src, edge]

src   : 0=关闭 1=CH1 2=CH2 3=D1 4=D2 5=D3   ✅ 与你们一致
edge  : 0=上升沿 1=下降沿 2=双边沿           ⚠️ 我们还支持"双边沿"(2)
level : 模拟 0~4095（越界会钳位到 4095）      ✅
pre   : 预触发点数，见上                       ✅
```

**⚠️ `SET_TRIGGER` 的负载是 6 字节，不是 4 字节。** 只发 4 字节会收到 `NACK 0x02`（长度不足）。

## 10. Q10 · 能否加测量字段或慢时基？

### 测量字段：**不建议加**

**架构原则：采集端只搬运，不做计算。**

三条理由：

1. **采集端是硬实时管道**，每 25ms 必须交一帧。插入过零检测/FFT 会挤占采样窗口，一旦掉帧你们那边就是卡顿。
2. **数据本来就在你们手上**。500 个点已经完整传过去了，采集端再算一遍是重复劳动 + 多一条命令往返。
3. **一致性**：你们画的波形和算出的频率来自同一批数据，屏幕上"看起来 5 个周期"和"读数 1kHz"永远对得上。如果采集端算、你们画，两边算法不一致就会被问住。

### 慢时基：**现状够用，暂不建议加**

课设要求的最低频率场景：

| 评分项 | 最低频率 | 10ms/格（100ms 窗）下 |
|---|---|---|
| 矩形波发生器（基础6）| 100 Hz | **10 个周期** ✅ |
| 波形触发（提高8）| 500 Hz | **50 个周期** ✅ |
| 频率/幅度测量（提高11）| 500 Hz | **50 个周期** ✅ |

**你们提到的 5Hz / 10Hz 慢信号不在课设要求范围内。**

### 如果确实要加

可以扩两档（`TIME_BASE = 5` = 20ms/格、`6` = 50ms/格），字段宽度够，不用改帧格式。但需要：

1. 我们扩 `ARR` 表和 `ACQ_TB_NUM`
2. 你们的档位数组同步扩到 7 档
3. `CAP` 加一位表示"支持慢时基"

**这是协议变更，双方确认后再动。现阶段不建议为它增加联调风险。**
